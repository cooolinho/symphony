# Grundlagen: Was KI-Agenten sind, welche Aufgaben sie übernehmen und wie sie Arbeit teilen (Stand November 2026)

Research date: 2026-11-12. Publication dates are given per source; anything from 2024/2025 is marked "(older)". Quotes are verbatim where in quotation marks; everything else is paraphrase of the cited page. Several numbers come from search-result summaries rather than a full read of the primary source; those are flagged "(via search snippet, not opened)".

## 1. How do Anthropic and other primary sources define an agent, and how do they distinguish agents from workflows?

### Takeaway
The stable primary definition (Anthropic, Dec 2024, still the reference in 2026) is a control-flow distinction: in a workflow, code decides what runs next; in an agent, the model decides. By 2026 Claude Code's own documentation applies the same axis to its product primitives ("who holds the plan": Claude turn by turn for subagents/skills, the script for dynamic workflows), so an "agent role" in a pipeline is best understood as a model-driven loop embedded as one step in a code-driven workflow.

### Cited Findings
- (older, Dec 19, 2024) Anthropic groups everything under "agentic systems" and splits them: "Workflows are systems where LLMs and tools are orchestrated through predefined code paths." Agents are "systems where LLMs dynamically direct their own processes and tool usage". — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- (older) The five workflow patterns and their stated fit — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents):
  - Prompt chaining: "ideal for situations where the task can be easily and cleanly decomposed into fixed subtasks."
  - Routing: "works well for complex tasks where there are distinct categories that are better handled separately".
  - Parallelization: "effective when the divided subtasks can be parallelized for speed"; two variants: sectioning ("Breaking a task into independent subtasks run in parallel.") and voting ("Running the same task multiple times to get diverse outputs.").
  - Orchestrator-workers: "well-suited for complex tasks where you can't predict the subtasks needed".
  - Evaluator-optimizer: "particularly effective when we have clear evaluation criteria".
- (older) When to use an agent at all: "Agents can be used for open-ended problems where it's difficult or impossible to predict the required number of steps". Default advice is the opposite direction: "we recommend finding the simplest solution possible, and only increasing complexity when needed. This might mean not building agentic systems at all." Cost of autonomy: "The autonomous nature of agents means higher costs, and the potential for compounding errors." — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- (older) Three core principles: simplicity of design, transparency (showing the agent's planning steps), and a carefully crafted agent-computer interface (tool documentation and testing; "Poka-yoke your tools. Change the arguments so that it is harder to make mistakes."). — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- The page itself now carries a note that much of the tooling described has changed since December 2024 and points to newer documentation; the definitions are unchanged. — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Claude Code documentation (current, fetched Nov 2026) defines a subagent operationally: "Subagents are specialized AI assistants that handle specific types of tasks." and "Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions." — [Claude Code docs, Create custom subagents](https://code.claude.com/docs/en/sub-agents)
- Claude Code's 2026 "dynamic workflows" restate the agent/workflow distinction as "who holds the plan": for subagents, skills and agent teams "Claude is the orchestrator: it decides turn by turn what to spawn or assign next, and every result goes into a context window. A workflow script holds the loop, the branching, and the intermediate results itself, so Claude's context holds only the final answer." Table row "Who decides what runs next": Subagents = "Claude, turn by turn"; Skills = "Claude, following the prompt"; Agent teams = "The lead agent, turn by turn"; Workflows = "The script". — [Claude Code docs, Dynamic workflows](https://code.claude.com/docs/en/workflows)
- Same doc, scale per primitive: subagents "A few delegated tasks per turn"; agent teams "A handful of long-running peers"; workflows "Dozens to hundreds of agents per run". — [Claude Code docs, Dynamic workflows](https://code.claude.com/docs/en/workflows)
- Definitions of the neighbouring primitives (current Claude Code docs) — [Claude Code docs, Extend Claude Code](https://code.claude.com/docs/en/features-overview):
  - Skill: "A skill is a markdown file containing knowledge, workflows, or instructions." Runs in the main conversation unless forked; "Skills are reusable content you can load into any context".
  - Subagent: "Isolated execution context that returns summarized results".
  - Hook: "Script, HTTP request, MCP tool call, prompt, or subagent triggered by events"; "Fires on its event without Claude deciding".
  - MCP: "Protocol for connecting to external services" (provides tools and data access, not knowledge).
  - CLAUDE.md: "Persistent context loaded every conversation".
- OpenAI's "A practical guide to building agents" (older, 2025) describes two multi-agent orchestration shapes: a manager pattern (central agent calls specialised agents as tools) and a decentralised handoff pattern (peers pass control), and advises staying with a single agent until tool count/complexity forces a split. (via search snippet and third-party summaries, PDF not opened) — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)

### Inferences
- For a catalogue, each entry should be classified on two independent axes: (1) who controls the flow (code vs. model) and (2) whether it runs in an isolated context. That yields the working vocabulary: deterministic check/hook (code, no model), tool (single capability the model may call), skill (instructions loaded into an existing context, model follows them), agent/subagent (own loop, own context, own tools), workflow (code that sequences agents).
- An issue-driven orchestrator such as Symphony is, in Anthropic's terms, a workflow (prompt chaining + routing over pipeline stages) whose steps are agents. The "40-50 roles" are therefore mostly worker definitions inside an orchestrator-workers or evaluator-optimizer shape, not autonomous peers.
- Evaluator-optimizer is the formal name for implement→review→fix loops; "voting" parallelisation is the formal name for multi-lens review/refutation panels.

### Gaps
- OpenAI's and Google's primary pattern documentation was not opened in full; only the OpenAI guide's outline is covered, via summaries. No claim about Google ADK or Microsoft patterns is made here.
- No source found that gives a formal, vendor-neutral definition of "agent role"; the term is used informally in all sources consulted.

## 2. What categories of tasks are agents demonstrably good at in software development, and which are they poor at?

### Takeaway
Published evidence supports agents on tasks with a machine-checkable success signal (tests, type checks, clear criteria) and on read-heavy exploration; evidence is weak or negative where success is a matter of intent and judgement (unprompted review comments, alignment with broader requirements) and where sub-tasks are tightly coupled. Hard numbers for individual pipeline stages are sparse and benchmark figures are harness-dependent.

### Cited Findings
- (older, Dec 2024) Why coding suits agents: "Code solutions are verifiable through automated tests;" "Agents can iterate on solutions using test results as feedback;" and the limit: "human review remains crucial for ensuring solutions align with broader system requirements." — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- (older, Jun 13, 2025) Research-style breadth-first work benefits from multi-agent: a multi-agent system (Opus 4 lead, Sonnet 4 subagents) "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval"; "token usage by itself explains 80% of the variance" on BrowseComp. Coding is called a weaker fit: "most coding tasks involve fewer truly parallelizable tasks than research"; domains needing "all agents to share the same context" are not a good fit. — [Anthropic, How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Exploration/locating is treated as a first-class delegated task in Claude Code: the built-in Explore subagent is read-only (Write and Edit denied) for "Fast codebase search and analysis" with thoroughness levels quick/medium/very thorough; the built-in Plan subagent is read-only research for plan mode. — [Claude Code docs, Create custom subagents](https://code.claude.com/docs/en/sub-agents)
- Task shapes Claude Code documents as fitting many-agent runs: auditing many files for the same issue with adversarial verification of each finding; fix-until-check-passes loops (e.g. `tsc --noEmit` until green or two rounds without progress); file-by-file migrations in isolated copies; per-file review merged into one ranked, deduplicated summary; flaky-test hunting until rounds find nothing new. — [Claude Code docs, Dynamic workflows](https://code.claude.com/docs/en/workflows)
- Automated code review, field data (Jul 2026): 31,073 review-comment/feedback pairs from 10,191 PRs in 239 GitHub repositories reviewed by CodeRabbit: "36.4% were accepted and 7.3% triggered discussion, while 56.3% were rejected." Rejections were mainly linked to invalid suggestions (false positives, redundant comments, out-of-scope comments), plus misalignment with developer intent and coding practices. — [Lin et al., arXiv 2607.03316](https://arxiv.org/abs/2607.03316)
- An MSR 2026 study (Chowdhury et al.) is reported to have found that 60.2% of closed code-review-agent-only PRs (of 3,109 AIDev PRs) had signal-to-noise ratios below 30%. (via search snippet from a secondary write-up, primary paper not located) — [secondary write-up](https://codex.danielvaughan.com/2026/04/19/code-review-agents-noise-problem-codex-cli-review-configuration/)
- Verification by a separate agent has a known failure mode, the "early victory problem": the verifier runs one or two tests, sees them pass and declares success. Mitigations named: concrete criteria, comprehensive checks, negative tests, explicit instruction to run the full suite. — [Anthropic/Claude blog, Building multi-agent systems: when and how to use them (Jan 23, 2026)](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Role-split pipelines can lose to a single agent: in one Anthropic experiment with planner, implementer, tester and reviewer agents, the subagents spent more tokens on coordination than on actual work ("telephone game": information degrades with each handoff). — [Claude blog, Building multi-agent systems (Jan 23, 2026)](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- (older, v3 Oct 2025) Multi-agent failure taxonomy MAST: 1,600+ annotated traces across 7 multi-agent frameworks, 14 failure modes in 3 categories: (i) system design issues, (ii) inter-agent misalignment, (iii) task verification. "Despite enthusiasm for Multi-Agent LLM Systems (MAS), their performance gains on popular benchmarks are often minimal." Tasks included coding. — [Cemri et al., arXiv 2503.13657](https://arxiv.org/abs/2503.13657)
- Long-horizon capability: METR's Time Horizon 1.1 (Jan 2026) expanded long tasks (8h+ human time) from 14 to 31, of which only 5 have measured human baselines; METR cautions that measurements above 16 hours are unreliable, and a March 2026 note says a modelling fix lowered recent models' 50% time horizons by up to 20%. The original 2025 estimate was a doubling roughly every 7 months; secondary sources in 2026 cite faster rates (4-5.5 months) and disagree with each other. (via search snippets) — [METR, Time Horizon 1.1](https://metr.org/blog/2026-01-29-time-horizon-1-1/); [METR note, Mar 2026](https://metr.org/notes/2026-03-20-impact-of-modelling-assumptions-on-time-horizon-results/)
- Human productivity evidence is unsettled. (older) METR's early-2025 RCT: experienced open-source developers took 19% longer with AI tools (CI +2% to +39%). METR's Feb 24, 2026 update on the follow-up (57 developers, 143 repositories, 800+ tasks): estimated change in task time -18% (CI -38% to +9%) for returning developers and -4% (CI -15% to +9%) for new ones; METR says "our data is only very weak evidence for the size of this increase" because of selection effects (30-50% of developers withheld tasks they did not want to do without AI; time measurement breaks down when developers run multiple agents concurrently). — [METR, uplift update](https://metr.org/blog/2026-02-24-uplift-update/)
- Benchmarks are harness-sensitive: one vendor guide states SWE-bench Pro has 1,865 tasks across 41 repositories (731 public), that scores are self-reported, and that changing the turn limit alone (50 to 250) can nearly triple scores; it also claims OpenAI audited the public split in July 2026 and found roughly 30% of tasks broken. (single vendor source, unverified against OpenAI or Scale) — [Verdent guide](https://www.verdent.ai/guides/answers/what-is-swe-bench-pro)
- A January 2026 concept paper on LLM-based agentic systems across the SDLC names the open problems as multi-agent orchestration, human-agent coordination, computational cost optimisation and data collection. — [Tang & Runkler, arXiv 2601.09822](https://arxiv.org/abs/2601.09822)

### Inferences
- Mapping to pipeline stages (inference from the findings above, not a published ranking):
  - Explore/locate: strong fit; read-only, high token volume, small answer. Vendor ships it as a built-in.
  - Implement with tests available: strong fit; test feedback closes the loop.
  - Test writing from acceptance criteria (black box): good fit and a good context boundary, because the tester needs the criteria and the public interface, not the implementer's history.
  - Verify/refute one concrete claim: good fit ("blackbox verification" needs little context transfer), provided the criteria are concrete and the early-victory problem is countered.
  - Review that produces unprompted findings: mixed; field acceptance near one third and majority rejection suggests findings need a refutation/filter stage before they reach a human or trigger rework.
  - Requirements analysis, design trade-offs, "is this what the owner meant": weakest evidence; the only primary statement is that human review "remains crucial" for alignment with broader requirements.
  - Triage/routing: fits the routing workflow pattern (classification into distinct categories); no published accuracy numbers found.
- Any stage whose output can be checked mechanically should have that check implemented as code, with the agent only doing the part that needs judgement.

### Gaps
- No published, stage-by-stage success rates (requirements, design, documentation, maintenance, triage) for coding agents were found; available numbers are for issue resolution benchmarks and code review acceptance.
- No verified, current SWE-bench Verified/Pro leaderboard figure was retrieved; the only detail comes from a vendor guide and an aggregator, both flagged as unverified.
- The MSR 2026 signal-to-noise study was not located as a primary source.
- No source found quantifying documentation-agent quality or maintenance/dependency-update agents.

## 3. What are the reasons to split work across several agents, and what does each reason imply about how a role should be cut?

### Takeaway
Anthropic's 2026 guidance names three situations where multiple agents reliably pay off — context protection, parallelisation (for thoroughness, not speed) and specialisation — and adds tool/permission restriction and cheaper models as benefits in the Claude Code docs. The consistent rule across Anthropic and Cognition is to cut roles along context boundaries, not along job titles; role-type splits of one coupled task (planner/implementer/tester/reviewer on the same change) are the documented anti-pattern, with independent verification as the named exception.

### Cited Findings
- The Agent SDK lists four benefits: context isolation ("only its final message returns to the parent"), parallelisation ("independent subtasks finish in the time of the slowest one rather than the sum of all of them"; example: `style-checker`, `security-scanner` and `test-coverage` running at once during a review), specialised instructions and knowledge (e.g. a `database-migration` subagent whose SQL/rollback knowledge "would be unnecessary noise in the main agent's instructions"), and tool restrictions (e.g. a `doc-reviewer` limited to Read and Grep). — [Claude Agent SDK docs, Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents)
- Benefits Claude Code lists for subagents: "Preserve context by keeping exploration and implementation out of your main conversation"; "Enforce constraints by limiting which tools a subagent can use"; "Reuse configurations across projects"; "Specialize behavior with focused system prompts for specific domains"; "Control costs by routing tasks to faster, lower-cost models like Haiku". — [Claude Code docs, Create custom subagents](https://code.claude.com/docs/en/sub-agents)
- Three situations where multi-agent consistently outperforms a single agent (Jan 23, 2026): context protection (helps most when a subtask generates more than 1,000 tokens that are mostly irrelevant to the main task; example: 2,000+ tokens of order history reduced to a 50-100 token summary), parallelisation (primary benefit is "thoroughness, not speed"), specialisation (when an agent has too many tools, spans unrelated domains, or must switch between conflicting behavioural modes; tool-selection trouble is flagged at roughly 20+ tools). "Outside these situations, the coordination costs typically exceed the benefits." — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Cost: multi-agent implementations typically use 3-10x more tokens than single-agent approaches for equivalent tasks, and parallelism often does not reduce total execution time. — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- (older, Jun 2025) Earlier Anthropic figures: "agents typically use about 4× more tokens than chat interactions," and "multi-agent systems use about 15× more tokens than chats."; "Multi-agent systems work mainly because they help spend enough tokens to solve the problem." — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Decompose by context, not by type of work: splitting by work type (one agent writes features, another tests, a third reviews) creates constant coordination overhead; "an agent building a feature should also write its tests, since it already has the context". Good boundaries: independent research paths, components with clean interfaces, blackbox verification. Poor boundaries: sequential phases of the same work, tightly coupled components, work requiring shared state. — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Verification subagent is the pattern that survives the telephone game because verification needs little context transfer; more capable orchestrators can sometimes verify directly, but verification subagents still help with weaker orchestrators, specialised tools or explicit checkpoints. — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- (older, Jun 12, 2025) Cognition's counter-position, two principles: "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results". Parallel subagents splitting one build are "very fragile"; default recommendation: "The simplest way to follow the principles is to just use a single-threaded linear agent." It notes Claude Code's subagent at that time was "usually only tasked with answering a question, not writing any code." — [Cognition, Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)
- Context as the scarce resource (older, Sep 29, 2025): as context grows, "the model's ability to accurately recall information from that context decreases"; "LLMs have an 'attention budget'". Sub-agent architectures are one of three long-horizon techniques (with compaction and structured note-taking); a subagent "returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)." Tool guidance: "curating a minimal viable set of tools for the agent". — [Anthropic, Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- When to keep work in the main agent rather than delegate: "The task needs frequent back-and-forth or iterative refinement"; "Multiple phases share significant context"; "You're making a quick, targeted change"; "Latency matters. A subagent that isn't a fork starts fresh and may need time to gather context". When to delegate: "a side task would flood your main conversation with search results, logs, or file contents you won't reference again". — [Claude Code docs, Create custom subagents](https://code.claude.com/docs/en/sub-agents)
- Independent judgement/adversarial verification as a first-class reason: a workflow "can have independent agents adversarially review each other's findings before they're reported, or draft a plan from several angles and weigh them against each other, so you get a more trustworthy result than a single pass." The bundled deep-research workflow "votes on each claim" and filters claims that do not survive cross-checking; a claim the verifiers could not check (rate limit, API error) is reported as unverified rather than refuted. — [Claude Code docs, Dynamic workflows](https://code.claude.com/docs/en/workflows)
- Limits on fan-out: a subagent may spawn subagents "up to three layers below the main conversation" by default; default cap of 20 concurrent subagents; workflows default to 16 concurrent agents and 1,000 agents per run; a "Large workflow" warning appears above 25 agents or 1.5 million projected tokens. — [Claude Code docs, Create custom subagents](https://code.claude.com/docs/en/sub-agents); [Claude Code docs, Dynamic workflows](https://code.claude.com/docs/en/workflows)
- (older) Operational risks of multi-agent: "Agents are stateful and errors compound."; synchronous lead agents waiting on subagents create "bottlenecks in the information flow between agents"; having subagents write outputs to external storage and return lightweight references reduces information loss. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Many subagent definitions have their own context cost: Claude Code warns when the combined descriptions of non-built-in subagents exceed 15,000 tokens, and when many subagents return detailed results "they can consume significant context". — [Claude Code docs, Create custom subagents](https://code.claude.com/docs/en/sub-agents)

### Inferences
What each splitting reason implies for cutting a role (derived from the findings above):

| Reason | A role cut for this reason should... | Typical pipeline roles |
| - | - | - |
| Context isolation | read a lot, return little (file:line pointers, a verdict, a short summary); no need for the caller's history | code explorer, log/trace analyst, dependency auditor, doc researcher |
| Parallelism (thoroughness) | work on an independent slice with no shared mutable state; one instance per item/lens | per-file reviewer, per-component auditor, per-criterion test designer |
| Independent judgement / adversarial verification | receive the artefact and the criteria, not the author's reasoning; default to "not proven"; one claim per call | finding verifier, refutation judge, black-box acceptance tester, design critic |
| Tool/permission restriction | be defined by what it may not do (read-only, no shell, no push); the restriction is the role | read-only reviewers, security inventory without shell |
| Cheaper model per task | be narrow and mechanical enough for a smaller model and lower effort | classifiers, triage, formatting of summaries, simple locate tasks |
| Specialisation (conflicting modes, tool overload) | bundle a domain's instructions/tools that would dilute a generalist prompt | framework specialists, database/migration engineer |

- A role that is justified only by a job title ("the tester", "the documenter") and works on the same coupled change with the same context is, by the cited guidance, more likely to cost tokens than to add quality; it is better expressed as a skill loaded into the implementing agent. A role justified by at least one row of the table above is a legitimate agent.
- Stage-level separation in an issue pipeline (requirements → implementation → review → documentation as separate runs) is a different thing from splitting one stage into sub-roles: stages hand over a durable artefact (issue text, branch, PR), which is the "clean interface" the guidance asks for. The telephone-game warning applies when the handover artefact is thin.
- With 40-50 roles, description budget and routing accuracy become a design constraint in themselves (15,000-token warning; overlapping descriptions cause wrong delegation), which argues for families of roles selected by the orchestrator's code rather than 50 roles visible to every agent.
- Observed in this environment (not a web source): the Symphony installation already exposes roles cut this way — explorer, design-critic, test-designer, bug-lens, convention-lens, finding-verifier, refutation-judge, security-inventory and Laravel specialists — each with an explicit "use when / not for" description and tool restrictions.

### Gaps
- No published quantitative comparison of "role-split" versus "context-split" pipelines beyond the one Anthropic experiment described qualitatively (no numbers given).
- The 3-10x (2026) and 15x (2025) token multipliers come from different contexts (general multi-agent vs. research system vs. chat baseline) and are not directly comparable.
- Cognition's position is from June 2025; no dated update from Cognition revising it was found on that page.

## 4. What does a well-defined agent role consist of?

### Takeaway
The vendor documentation converges on a small contract: a trigger description the orchestrator can route on, a self-contained task brief (objective, output format, tool guidance, boundaries), a restricted tool set, an explicit model/effort choice and a bounded run (turn limit, effort budget). Claude Code's subagent frontmatter maps one-to-one onto these parts.

### Cited Findings
- (older, Jun 2025) Each delegated task needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; without them agents duplicate work or leave gaps. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- (older) Effort-scaling rules embedded in prompts: simple fact-finding "1 agent with 3-10 tool calls"; direct comparisons 2-4 subagents with 10-15 calls each; complex research "more than 10 subagents with clearly divided responsibilities". — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Subagent definition fields in Claude Code (only `name` and `description` required) — [Claude Code docs, Create custom subagents](https://code.claude.com/docs/en/sub-agents):
  - `description`: "When Claude should delegate to this subagent."
  - `tools` (allowlist; inherits all if omitted) and `disallowedTools` (denylist).
  - `model`: `sonnet`, `opus`, `haiku`, `fable`, a full model ID, or `inherit`; resolution order is per-invocation parameter, then frontmatter, then `CLAUDE_CODE_SUBAGENT_MODEL`, then the main conversation's model.
  - `effort`: `low`, `medium`, `high`, `xhigh`, `max`.
  - `maxTurns`: maximum agentic turns; output at the limit is marked partial and the subagent can be resumed.
  - `permissionMode`, `skills` (full content injected at startup), `mcpServers`, `hooks` (scoped to the subagent), `memory` (`user`/`project`/`local`), `background`, `isolation: worktree`, `omitClaudeMd`.
- What a subagent starts with: "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read." It receives its own system prompt (not the Claude Code system prompt), the task message, CLAUDE.md and git status (except Explore/Plan), and preloaded skills. — [Claude Code docs, Create custom subagents](https://code.claude.com/docs/en/sub-agents)
- Description guidance: keep descriptions brief and "move detail into each subagent's system prompt, which only loads when that subagent runs"; phrases like "use proactively" encourage delegation. — [Claude Code docs, Create custom subagents](https://code.claude.com/docs/en/sub-agents)
- Routing depends on descriptions being distinct: for skills, "If descriptions are vague or overlap, Claude may load the wrong skill or miss one that would help." — [Claude Code docs, Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Output contract can be enforced structurally: in workflows, passing a `schema` makes the subagent return JSON matching the shape; validation is retried up to five times, then the call fails. — [Claude Code docs, Dynamic workflows](https://code.claude.com/docs/en/workflows)
- Claude Agent SDK (the base Symphony is built on): subagents are defined programmatically via the `agents` option of `query()` as `AgentDefinition` objects (recommended for SDK apps) or as `.claude/agents/` files; programmatic definitions override files with the same name. Required fields: `description` ("Natural language description of when to use this agent") and `prompt` ("The agent's system prompt defining its role and behavior"). Optional: `tools`, `disallowedTools` (incl. `mcp__server__*` patterns), `model`, `skills` (at most the first 32 preloaded), `memory`, `mcpServers`, `maxTurns` (output marked partial at the limit, resumable), `background`, `omitClaudeMd`, `effort` (level or number), `permissionMode`. — [Claude Agent SDK docs, Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents)
- Input contract is literally the prompt string: "The only content you pass from parent to subagent is the Agent tool's prompt string, so include any file paths, error messages, or decisions the subagent needs directly in that prompt." The subagent does not receive the parent's history, tool results or system prompt. — [Claude Agent SDK docs, Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents)
- Tool restriction semantics: "A tool you leave out isn't in the subagent's session at all: Claude works without it, with no permission prompt or error." Documented combinations: read-only analysis (Read, Grep, Glob), test execution (Bash, Read, Grep), code modification (Read, Edit, Write, Grep, Glob). — [Claude Agent SDK docs, Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents)
- Roles can be parameterised at runtime: the SDK doc shows a factory that builds a security reviewer with "strict" vs "balanced" prompt and picks `opus` for strict, `sonnet` otherwise ("use a more capable model for high-stakes reviews"). — [Claude Agent SDK docs, Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents)
- Run-level bounds in the SDK: spawn depth (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, default 3; `1` disables nesting), concurrency (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, default 20) and spend (`maxBudgetUsd` / `max_budget_usd`, no default limit; at the cap it refuses new subagents, stops background ones and ends with `error_max_budget_usd`). The doc notes Claude Opus 5 "delegates to subagents more readily than earlier models", so these limits matter most there; the `claude_code` preset adds a line telling Opus 5 not to call the Agent tool unless asked, a custom system prompt does not. — [Claude Agent SDK docs, Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents)
- Subagent output is scanned before the parent reads it (since v2.1.210): imitated control tags and turn markers are neutralised, and a `[harness: ...]` marker is prepended for control-tag or permission-config matches; the text is never removed or reworded. An API error that ends a subagent early "is never delivered as its result". — [Claude Agent SDK docs, Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents)
- Return size: a subagent should return a condensed summary ("often 1,000-2,000 tokens"). — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Stop conditions documented for loops: "until the type check passes or two rounds in a row make no progress"; "stop once two rounds in a row find nothing new"; verification retry limit of 3 attempts in Anthropic's sample. — [Claude Code docs, Dynamic workflows](https://code.claude.com/docs/en/workflows); [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- (older) System prompt "right altitude": between hard-coded brittle logic and vague high-level guidance ("the Goldilocks zone between two common failure modes"). — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- (older) Evaluation of roles: "Start evaluating immediately with small samples." (about 20 queries), LLM judge with a rubric plus human testing. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
A role card template that covers every element the sources require (synthesis, not a published template):

1. Name and one-line purpose.
2. Trigger: "use when ..." plus explicit "not for ..." (negative scope prevents overlap between 40-50 roles).
3. Why it is an agent: which splitting reason(s) from section 3 justify isolation.
4. Input contract: what the caller must pass (the role sees nothing else): artefact, criteria, scope limits, base commit, etc.
5. Output contract: fixed shape (verdict + evidence as file:line, or a schema), size cap, what counts as "nothing found".
6. Tools and permissions: allowlist/denylist, read-only or not, worktree isolation.
7. Model and effort: smallest model that passes the role's eval; effort level.
8. Budget and stop condition: max turns, call budget, "no progress in N rounds", what to return when the limit is hit (partial, flagged).
9. Failure/escalation behaviour: unverifiable is reported as unverified, not as refuted or confirmed.
10. Acceptance check: a small eval set or a deterministic check on the output format.

- Invocation cardinality (once per change, once per finding, once per lens) belongs in the trigger, because it determines cost and independence.

### Gaps
- No primary source prescribes a canonical "role card"; the template is assembled from separate recommendations.
- No published guidance on the right number of roles for a pipeline or on measured routing accuracy as the role count grows, beyond the 15,000-token description warning.

## 5. Which task types are better served by a skill, a hook or a deterministic script instead of an agent?

### Takeaway
Anthropic's 2026 rule set is explicit: always-on facts go in CLAUDE.md, scoped constraints in path rules, repeatable procedures in skills, noisy side tasks in subagents, and anything that must happen (or never happen) every time in a hook or other deterministic mechanism — "A real guardrail needs to be deterministic." An agent is only warranted where judgement plus isolation is needed.

### Cited Findings
- Summary decision rules (Jun 18, 2026): always-on facts → CLAUDE.md; scoped constraints → path-scoped rules; repeatable procedures → skills ("Instructions that are procedural, like deploy workflows, release checklists, or review processes, belong in a skill."); noisy side tasks → subagents; guaranteed actions or blocks → hooks ("Use hooks for anything that should happen deterministically"). — [Claude blog, Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- "A real guardrail needs to be deterministic."; "A PreToolUse hook can inspect any tool call and exit code 2 to deny it."; managed settings are "the only way to enforce a deterministic, organization-wide guardrail." — [Claude blog, Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- Hook vs. skill: "Use a hook when the action must happen the same way every time and doesn't need Claude to think. For example: format on save, reject `rm -rf /`, post a Slack message when a session ends." "Use a skill when Claude should decide how to apply the steps, or when the content is knowledge rather than a script." "An instruction like 'never edit `.env`' in CLAUDE.md or a skill is a request, not a guarantee. A `PreToolUse` hook that blocks the edit is enforcement." — [Claude Code docs, Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Hook characteristics: "Determinism: Fires on its event without Claude deciding"; context cost "Zero unless the hook returns output"; best for "Linting after edits, blocking unsafe commands, logging, notifications". Hook output can feed the agent: "A `PostToolUse` hook that runs your linter feeds results back as text Claude reads; a `/fix-lint` skill tells Claude how to resolve them." — [Claude Code docs, Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Hooks give "deterministic control: certain actions always happen rather than relying on the LLM to choose to run them"; for decisions needing judgement there are prompt-based and agent-based hooks that use a model to evaluate a condition. — [Claude Code docs, Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Skill vs. subagent: skill "Adds to your main window", best for "Reference material, invocable workflows"; subagent "Uses a separate window", best for "Tasks that read many files, parallel work, specialized workers". "Consider Skills instead when you want reusable prompts or workflows that run in the main conversation context rather than isolated subagent context." Skills run in the main thread so each step can be seen and steered. — [Claude Code docs, Extend Claude Code](https://code.claude.com/docs/en/features-overview); [Claude Code docs, Create custom subagents](https://code.claude.com/docs/en/sub-agents); [Claude blog, Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- Combination patterns: "A subagent can preload specific skills (`skills:` field). A skill can run in isolated context using `context: fork`."; "Skill + Subagent: A skill spawns subagents for parallel work" (e.g. an `/audit` skill starting security, performance and style subagents). — [Claude Code docs, Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Skills with side effects should be user-invoked only (`disable-model-invocation: true`). — [Claude Code docs, Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Code intelligence (LSP) as a tool replaces agentic search for symbol lookup: "Symbol lookups often replace broad file reads, so net context use can go down." — [Claude Code docs, Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Before adding agents, cheaper fixes are recommended: better prompting or Tool Search, which is said to reduce token usage by up to 85%. — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- (older) Agents should be the last resort: "finding the simplest solution possible, and only increasing complexity when needed." — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

### Inferences
Decision ladder for each candidate entry in a role catalogue (derived from the rules above):

1. Is the outcome decidable by code (lint, format, type check, test run, coverage threshold, secret scan, licence check, commit-message format, branch protection, path rules, schema validation of an agent's report)? → deterministic script/hook/CI check. No agent.
2. Is it knowledge or a fixed procedure the working agent should apply in its own context (coding conventions, framework idioms, release checklist, PR description format, "how we write migrations")? → skill (or rule), loaded into the implementing agent. No separate agent.
3. Is it access to an external system (issue tracker, database, browser)? → tool/MCP, optionally with a skill explaining its use.
4. Does it need judgement and at least one of: large read volume with a small result, independence from the author's reasoning, parallel independent slices, a restricted permission set, or a cheaper model? → agent.
5. Does it need many agents with a fixed quality pattern (fan-out, verify each finding, merge)? → workflow in code that calls agents; in an orchestrator like Symphony this is the pipeline's own stage logic.

- Consequence for a 40-50 entry catalogue: a realistic catalogue is a mix. Entries such as "formatter", "linter", "test runner", "changelog format checker" or "report validator" are checks; entries such as "coding standards expert" or "release-notes writer for a known format" are skills; what remains as agents are the roles in the section 3 table.
- A deterministic check and an agent often pair up: the check produces the signal (failing test, lint output, type errors), the agent interprets and fixes; the fix-until-green loop then has a code-defined stop condition.
