# Limits and costs of many specialised agent roles (40-50); subagent vs. skill vs. hook vs. deterministic check

State: 2026-11-12. All Claude Code / Agent SDK statements were read from the live documentation on that day; version-dependent statements are marked "(version: ...)". "MEASURED" = published number from an experiment or dataset; "OPINION" = argument or heuristic without data; "DOC" = vendor documentation of behaviour.

## 1. Multi-agent overhead: token multiplier, coordination failures, error propagation, context loss at handoffs

### Takeaway
Published evidence agrees that multi-agent pays off for parallelisable, breadth-first, context-heavy work and harms sequential, tightly coupled work, which is what most coding is; the cost is 3-10x tokens against a single agent (Anthropic 2026) and up to 15x against chat (Anthropic 2025). Splitting by role or phase (planner, implementer, tester, reviewer) is explicitly named by Anthropic as the pattern that fails; verification by a fresh-context agent is the one role split that is consistently reported to work.

### Cited Findings
- MEASURED (Anthropic, internal): "agents typically use about 4x more tokens than chat interactions", "multi-agent systems use about 15x more tokens than chats". — [Anthropic, How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- MEASURED: Opus 4 lead + Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval"; token usage alone explained 80% of performance variance on BrowseComp (three factors together 95%). This is a research/search task, not coding. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Poor fit stated by the same article: "domains that require all agents to share the same context or involve many dependencies between agents are not a good fit"; "most coding tasks involve fewer truly parallelizable tasks than research"; "LLM agents are not yet great at coordinating and delegating to other agents in real time". — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Observed early failure modes there: spawning 50 subagents for simple queries, endless searching for nonexistent sources, subagents distracting each other with updates. Each subagent needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; vague delegation caused duplicated work and gaps. Scaling rule embedded in the prompt: simple fact-finding 1 agent with 3-10 tool calls; comparisons 2-4 subagents with 10-15 calls each; complex research more than 10 subagents. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Anthropic, 2026-01-23: "multi-agent implementations typically use 3-10x more tokens than single-agent approaches for equivalent tasks" (duplicated context, coordination messages, summarising at handoffs). Presented as a typical figure, no dataset given. — [Claude blog, Building multi-agent systems: when and how to use them](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Same article: three situations where multiple agents "consistently outperform" one: context protection (subtask produces high-volume, mostly irrelevant output), parallelisation ("the primary benefit of parallelization is thoroughness, not speed"; runs often take longer overall), specialisation (tool selection, conflicting system prompts, deep domain context). — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Same article, against role/phase splits: dividing by problem type (feature writing, testing, review) "creates constant coordination overhead"; sequential phases of the same work share too much context to split; recommended is context-centric decomposition, "an agent handling a feature should also handle its tests"; role-based splits create a "telephone game" where each handoff loses fidelity; one reported experiment with planner, implementer, tester and reviewer agents found the subagents "spent more tokens on coordination than on actual work" (anecdote, no numbers). — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Same article: "Verification subagents succeed because they sidestep the telephone game problem" (the verifier needs artifact, success criteria and tools, not the build history). Known failure: "early victory", verifier declares success after a few tests; fix is an explicit instruction such as "You MUST run the complete test suite before marking as passed". — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- MEASURED (MAST, Cemri et al., arXiv 2503.13657v3, Oct 2025): 1,642 annotated traces from 7 multi-agent frameworks, 14 failure modes in 3 categories; failure rates of the evaluated systems 41% to 86.7%. Mode shares: disobey task spec 11.8%, disobey role spec 1.5%, step repetition 15.7%, loss of conversation history 2.8%, unaware of termination 12.4% (system design, sum about 44%); conversation reset 2.2%, fail to ask for clarification 6.8%, task derailment 7.4%, information withholding 0.85%, ignored other agent's input 1.9%, reasoning-action mismatch 13.2% (inter-agent misalignment, sum about 32%); premature termination 6.2%, no/incomplete verification 8.2%, incorrect verification 9.1% (verification, sum about 24%). Category sums are my addition of the per-mode figures. — [Why Do Multi-Agent LLM Systems Fail? v3](https://arxiv.org/html/2503.13657v3)
- MAST conclusions: "MAS failure is not merely a function of challenges in the underlying model" (design matters); gains of MAS "often remain minimal compared to single-agent frameworks" or best-of-N sampling (no exact numbers); interventions on ChatDev: clearer role/hierarchy +9.4% task success, added high-level verification step +15.6%, both judged insufficient by the authors. Caveat: frameworks studied are 2023-2024 generation (ChatDev, MetaGPT, AG2 etc.) with GPT-4o/Claude 3.7 class models. — [Why Do Multi-Agent LLM Systems Fail? v3](https://arxiv.org/html/2503.13657v3)
- MEASURED (Google Research / MIT, arXiv 2512.08296): 180 configurations, 5 architectures (single, independent, centralized, decentralized, hybrid), 4 benchmarks, 3 model families. Centralized coordination +80.9% on a parallelisable financial-reasoning task; on sequential planning (PlanCraft) "every multi-agent variant we tested degraded performance by 39-70%". Independent agents amplified errors 17.2x, centralized orchestration contained it to 4.4x ("the orchestrator effectively acts as a validation bottleneck"). A coding agent with "16+ tools" is given as an example where coordination overhead rises disproportionately. Predictive model R2 = 0.513, picks the best architecture for 87% of unseen configurations. — [Google Research blog, Towards a science of scaling agent systems](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/); paper: [arXiv 2512.08296](https://arxiv.org/html/2512.08296v2)
- OPINION (Cognition, Walden Yan, 2025-06-12): two principles, "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results"; conclusion "running multiple agents in collaboration only results in fragile systems" (qualified to 2025). Notes that Claude Code subagents then only answered well-defined questions and did not write code in parallel because "the subtask agent lacks context from the main agent". No benchmarks; example is hypothetical; author works for a vendor of a single-agent product. — [Cognition, Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)
- DOC (handoff mechanics in the SDK): "The only content you pass from parent to subagent is the Agent tool's prompt string, so include any file paths, error messages, or decisions the subagent needs directly in that prompt"; only the subagent's final message returns, and "the parent receives the subagent's final report, but may summarize it in its own response". — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- DOC: Opus 5 "verifies its own work without being told to"; explicit instructions such as "use a subagent to verify" cause over-verification and should be removed; "Delegation is worthwhile for genuinely independent, sizeable tracks of work, but it multiplies cost and time when applied to small tasks." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)

### Inferences
- The owner's pipeline (analyst, architect, developer, test engineer, docs, reviewer, security auditor) is a phase split at the orchestrator level. The published warnings about phase splits apply to the handoffs between those stages, not only to subagents inside a stage. What saves such a pipeline is that handoffs are persisted artifacts (issue, PR, diff), which is a "shared full trace" in the Cognition sense, rather than a summary message.
- Of 40-50 candidate roles, the evidence supports three kinds as subagents: (a) context-protecting explorers, (b) parallel independent lenses over one artifact (review, audit), (c) fresh-context verifiers/refuters. Roles that are a phase of the same work (e.g. "implement the migration" inside the developer stage) are better as skills loaded into the acting agent.
- The MAST shares suggest where additional roles add failure surface: about a quarter of failures are verification failures, and "step repetition" and "unaware of termination" (28% together) are harness problems that a role prompt cannot fix but turn caps and structured results can.
- Centralized orchestration (17.2x vs 4.4x error amplification) supports keeping the orchestrator, not peer agents, as the single place where results are validated.

### Gaps
- No published controlled measurement of role-specialised subagents versus one generalist agent on real software-engineering issues with 2026 models (Opus 5.x, Fable 5.x). The MAST and Google numbers come from older models or non-coding benchmarks.
- The 3-10x figure has no public dataset; the "coordination tokens exceed work tokens" experiment is an anecdote.
- MAST per-framework success rates and the AG2 case study were not readable in the fetched part of the paper.

## 2. Subagent selection in Claude Code / Agent SDK, selection accuracy, under-delegation, context cost of descriptions

### Takeaway
Selection is model-decided from the `description` text unless the caller names the agent; there is no documented accuracy figure for 40-50 descriptions, only a 15,000-token startup warning for combined descriptions and a 1%-of-context budget for the skill listing. Under-delegation is documented and expected: Anthropic's own guidance tells Opus 5 to delegate only large independent work, and the `claude_code` preset tells Opus 5 not to call the Agent tool unless asked, so a low spontaneous delegation rate (48 of 1,686) is consistent with intended behaviour rather than a defect.

### Cited Findings
- DOC: "Claude uses each subagent's description to decide when to delegate tasks." To encourage it, "include phrases like 'use proactively' in your subagent's description field". Guaranteed invocation: naming the agent in the prompt, `@agent-<name>` mention, or running the whole session as that agent (`claude --agent <name>`, `agent` setting). — [Claude Code, Subagents](https://code.claude.com/docs/en/sub-agents)
- DOC (SDK): "Claude automatically decides when to invoke subagents based on the task and each subagent's description"; "To guarantee Claude uses a specific subagent, mention it by name in your prompt ... This bypasses automatic matching". Troubleshooting section "Claude not delegating to subagents" offers only two remedies: explicit prompting and a clearer description. — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- DOC: Allowlist syntax `tools: Agent(worker, researcher), Read, Bash` in a main-thread agent, "This is an allowlist: only the worker and researcher subagents can be spawned"; `Agent` alone allows any type; omitting it prevents spawning. The parenthesised list is ignored inside a subagent definition (it only applies to the main-thread agent). Blocking individual types: `permissions.deny` with `Agent(Explore)` or `disallowedTools: ["Agent(fork)"]`. — [Claude Code, Subagents](https://code.claude.com/docs/en/sub-agents); [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- DOC: Built-in `general-purpose` is always spawnable when the Agent tool is called without `subagent_type`; `CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1` removes it. From Claude Code v2.1.302 the model can also start a `fork` subagent with nothing configured (version: v2.1.302+). — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- DOC, context cost of agent descriptions: "Those descriptions take up context, so keep them short. When the combined descriptions of your subagents, except the built-in ones, exceed 15,000 tokens, Claude Code shows a warning at startup." Detail belongs in the system prompt, which "only loads when that subagent runs". — [Claude Code, Subagents](https://code.claude.com/docs/en/sub-agents)
- DOC: No limit on total subagents per session; default 20 concurrent (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), then `Concurrent subagent limit reached`. Agent `name` max 256 characters. — [Claude Code, Subagents](https://code.claude.com/docs/en/sub-agents)
- DOC, skills: the listing "always contains every skill name, but if you have many skills, Claude Code drops some descriptions to fit the listing's character budget, which removes the keywords Claude needs to match your request. The budget scales at 1% of the model's context window." Descriptions are dropped starting with the least-invoked skills. Each entry's `description` + `when_to_use` is capped at 1,536 characters. Tunable via `skillListingBudgetFraction`, `SLASH_COMMAND_TOOL_CHAR_BUDGET`, `skillListingMaxDescChars`; `skillOverrides` value `"name-only"` lists a skill without description; `disable-model-invocation: true` removes it from context entirely. `/context` reports the post-budget size (version: v2.1.196+). — [Claude Code, Skills](https://code.claude.com/docs/en/skills)
- DOC: "Every skill in the skill listing adds to your context on every turn, whether or not Claude ever uses it." `/skill-doctor` reports per-skill context cost and usage and flags never-invoked skills (version: v2.1.252+). — [Claude Code, Skills](https://code.claude.com/docs/en/skills)
- DOC, selection quality: "If descriptions are vague or overlap, Claude may load the wrong skill or miss one that would help"; too many features add "noise that makes Claude less effective; skills may not trigger correctly". — [Claude Code, Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- DOC, under-delegation by design: "Claude Opus 5 delegates to subagents more readily than earlier models"; with the `claude_code` system-prompt preset and Opus 5, "Claude Code adds a line to its system prompt telling Claude not to call the Agent tool unless it's asked to. The Agent tool stays available." With a custom or omitted system prompt that line is absent. Recommended instruction: "Delegate to a subagent only for large tasks that are genuinely independent and parallelizable ... Do not delegate work you can finish yourself in a handful of tool calls, and do not use subagents to verify or double-check your own work." — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents); [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Related evidence on selection among many options (tools, not agents): Anthropic states "An agent with too many tools (often 20+) struggles to select the appropriate one" and "When an agent has 15-20+ tools, the model spends significant context and attention understanding its options"; recommends trying Tool Search first (can "reduce token usage by up to 85%"). — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- MEASURED (RAG-MCP, Gan and Sun, arXiv 2505.03275, May 2025): retrieval-preselected tool descriptions reached 43.13% tool-selection accuracy against 13.62% for the all-tools-in-prompt baseline, with roughly half the prompt tokens (1,084 vs 2,134). This compares two methods, not accuracy against tool count; secondary summaries quoting "85% at 5 tools to 45% at 20 tools" could not be verified against the paper text. Older, smaller models. — [arXiv 2505.03275](https://arxiv.org/abs/2505.03275v1)
- DOC, measuring trigger accuracy: generate should-trigger and should-not-trigger prompts, measure the hit rate, propose description edits (skill-creator "description tuning"); for plugin skills a `tool_used: Skill` grader in `claude plugin eval` measures how often a skill triggers across realistic prompts. — [Claude Code, Skills](https://code.claude.com/docs/en/skills)

### Inferences
- With per-pipeline-role allowlists, a stage never sees all 40-50 descriptions, only its own allowlisted handful. The selection problem is therefore per stage (ideally under about 5-8 choices), and the 15,000-token warning is far away: 50 descriptions at roughly 60-100 tokens each are about 3,000-5,000 tokens even if all were visible. Context cost of descriptions is not the binding constraint; overlap between descriptions and the model's reluctance to delegate are.
- If descriptions are registered globally but the hook denies most of them per stage, the model still reads descriptions it may not use and can pick a denied agent; registering only the allowlisted agents per `query()` call (the SDK's `agents` option is per call) avoids both the noise and the denied calls.
- The earlier internal finding (48 of 1,686 runs delegated) matches documented behaviour: delegation is model-optional, the vendor's own prompts discourage it for small tasks, and the documented remedy is explicit invocation. A role that must run should be invoked by the orchestrator or named in the stage prompt under a stated condition, not left to description matching.
- There is a direction conflict across model generations: Opus 5 over-delegates relative to earlier models (hence the damping instruction), earlier models under-delegate. Delegation-rate baselines are therefore model-version-dependent and must be re-measured after each model change.

### Gaps
- No published accuracy curve for subagent or skill selection as the number of descriptions grows (10, 20, 50) on current Claude models. The 15,000-token warning and the 1% budget are the only quantitative thresholds found.
- Whether the "do not call the Agent tool unless asked" line applies to Opus 5.5 / Fable 5.x under the preset was not stated on the pages read; the docs name Opus 5 only.
- The last 17,000 characters of the Claude Code subagents page (fork details, some examples) were not read.

## 3. Subagents vs. skills vs. hooks vs. slash commands vs. MCP vs. plugins; SDK features relevant for many roles

### Takeaway
The documentation draws the lines by context and determinism: a subagent is an isolated context that returns a summary, a skill is on-demand instructions loaded into whichever context invokes it, a hook is deterministic enforcement outside the model, MCP is access to external systems, and a plugin is only packaging. For a 40-50 role catalogue the decisive point is that "role" does not imply "subagent": a role that needs neither isolation, nor its own tool limits, nor parallelism is a skill, and a rule that must always hold is a hook or an ordinary deterministic check.

### Cited Findings
- DOC, purpose table: Skill = "Reusable content, reference docs, repeatable tasks"; Subagent = "Context isolation, parallel tasks, specialized workers"; MCP = "External data or actions"; Hook = "Automation that must run on every matching event"; Dynamic workflow = "Work that outgrows a handful of subagents, or findings you want cross-checked"; Plugins "are the packaging layer. A plugin bundles skills, hooks, subagents, and MCP servers into a single installable unit". — [Claude Code, Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- DOC, skill vs subagent: skill "adds to your main window", subagent "uses a separate window with its own input and output tokens"; "Use a subagent when you need context isolation or when your context window is getting full." They combine both ways: subagent `skills:` field preloads full skill content; skill `context: fork` runs the skill as the task of a subagent chosen by `agent:`. — [Claude Code, Extend Claude Code](https://code.claude.com/docs/en/features-overview); [Claude Code, Skills](https://code.claude.com/docs/en/skills)
- DOC, when to use a subagent: "The task produces verbose output you don't need in your main context", "You want to enforce specific tool restrictions or permissions", "The work is self-contained and can return a summary". Stay in the main conversation when "the task needs frequent back-and-forth or iterative refinement" or for "a quick, targeted change". "Consider Skills instead when you want reusable prompts or workflows that run in the main conversation context rather than isolated subagent context." — [Claude Code, Subagents](https://code.claude.com/docs/en/sub-agents)
- DOC, hook vs skill: hook "fires on its event without Claude deciding", context cost "zero unless the hook returns output"; skill: "Claude interprets the instructions; outcome can vary". "Put guardrails in hooks. An instruction like 'never edit .env' in CLAUDE.md or a skill is a request, not a guarantee. A PreToolUse hook that blocks the edit is enforcement. If a rule must hold every time, make it a hook rather than a prompt instruction." Hook handlers can be a shell command, HTTP request, MCP tool call, LLM prompt or subagent. — [Claude Code, Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Anthropic blog, 2026-06-18: "A real guardrail needs to be deterministic, and the enforcement methods are hooks and permissions"; "The model choosing to run a formatter is different from the formatter running automatically"; prompt and agent hooks are the exception because they use model judgment; "Use a skill when you want the procedure to play out inside the main thread so you can see and steer each step"; subagents for side tasks whose intermediate output is not needed; "Generally, the more instructions you provide using this method, the less strictly Claude will follow them" (about appended system prompts). — [Claude blog, Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- DOC, slash commands: merged into skills. `.claude/commands/deploy.md` and `.claude/skills/deploy/SKILL.md` both create `/deploy`; skills add supporting files, frontmatter control and automatic loading. `disable-model-invocation: true` = only a human/caller can trigger, description not in context; `user-invocable: false` = only the model can trigger. — [Claude Code, Skills](https://code.claude.com/docs/en/skills)
- DOC, skill frontmatter relevant to roles: `allowed-tools` (pre-approval for the invoking turn, not a restriction), `model`, `effort`, `paths` (auto-load only for matching files), `context: fork` + `agent`, `hooks`. SKILL.md should stay under 500 lines. After compaction the most recent invocation of each skill is re-attached with its first 5,000 tokens, combined budget 25,000 tokens. — [Claude Code, Skills](https://code.claude.com/docs/en/skills)
- DOC, MCP: tool names load at session start, full schemas deferred (tool search on by default), "idle MCP tools consume minimal context". — [Claude Code, Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- DOC, per-agent configuration (file frontmatter and SDK `AgentDefinition`): `description`, `prompt`, `tools`, `disallowedTools`, `model` (alias, full ID or `inherit`), `effort` (`low`..`max`), `maxTurns`, `skills` (preload, first 32 distinct names), `mcpServers`, `memory` (`user`/`project`/`local`), `background`, `permissionMode`, `omitClaudeMd` (TS SDK v0.3.271+, not in Python), `autoCompactWindow` (TS SDK v0.3.296+), plus file-only `isolation: worktree`, `hooks`, `color`. Model resolution order: per-invocation `model` parameter, frontmatter `model`, `CLAUDE_CODE_SUBAGENT_MODEL`, main model. — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents); [Claude Code, Subagents](https://code.claude.com/docs/en/sub-agents)
- DOC, `maxTurns`: at the limit the output is returned marked as partial and the agent can be resumed (partial marking version: Claude Code v2.1.246+). — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- DOC, nesting: default is now three layers of subagents below the main agent; `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` turns nesting off; at the limit the bottom agent "does its delegated work itself". Per-agent: omit `Agent` from `tools`. Limits described for TS SDK v0.3.219 / Python SDK v0.2.127 (Claude Code v2.1.219) and later; "On earlier releases, some of these limits are missing or default differently". — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- DOC, spend cap: `maxBudgetUsd` / `max_budget_usd` counts subagent requests, refuses further spawns (`Budget limit reached`), stops running background subagents and ends the query with `error_max_budget_usd`. — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- DOC, background: a subagent spawned by the main agent runs in the background by default (`status: "async_launched"`, report arrives in a later turn); Claude waits when its next action needs the report; `background: true` pins background. Background subagents get a reduced built-in tool set. An API error that ends a subagent early (e.g. rate limit) "is never delivered as its result". — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- DOC, what a subagent starts with: own system prompt (not the Claude Code system prompt), the Agent tool prompt, project CLAUDE.md (unless `omitClaudeMd`), tool definitions, preloaded skills; not the parent history or parent system prompt. A `fork` instead copies the parent conversation, system prompt and tools. — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- DOC, hooks for observability: `SubagentStart` and `SubagentStop` fire in the main session with a matcher on the agent's `name`; frontmatter `Stop` hooks of an agent are converted to `SubagentStop` when it runs as a subagent. Detection in the stream: `tool_use` blocks named `Agent` (named `Task` before Claude Code v2.1.63 and still `Task` in the `system:init` tool list), `parent_tool_use_id` on messages from inside a subagent, `agent_id` (TS SDK v0.3.292+). — [Claude Code, Subagents](https://code.claude.com/docs/en/sub-agents); [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- DOC, scale-out: "Subagents work well for a few delegated tasks per turn. For runs that coordinate dozens to hundreds of agents, use the Workflow tool, which moves the orchestration into a script the runtime executes outside the conversation context" (TS SDK v0.3.149+). "With subagents, Claude decides turn by turn what runs next. In a workflow, the script decides." — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents); [Claude Code, Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- DOC, safety of returned text: from v2.1.210 Claude Code scans a subagent's final message for instruction-shaped patterns (control-tag imitation, permission-config mentions, turn markers) and neutralises or flags them without deleting text. — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)

### Inferences
- Decision rule that follows from the docs, in order: (1) Can the property be checked without a model (lint, tests, schema, path rule, diff size)? Then a deterministic check or a command hook; cost zero tokens. (2) Must it happen every time at a lifecycle event? Hook. (3) Is it knowledge or a procedure the acting agent should apply with judgment in its own context? Skill (with `paths` or `disable-model-invocation` to keep it out of the listing when irrelevant). (4) Does it need a fresh or isolated context, different tool limits, a different model/effort, or parallel execution? Subagent. (5) Does it need an external system? MCP tool. (6) Must the bundle be reused across repositories? Plugin.
- Many "roles" in a 50-role catalogue can be one generic subagent definition plus a skill per speciality (`skills:` preload or `context: fork` with `agent:`), which keeps the number of agent descriptions low while keeping the specialised instructions. The SDK's dynamic agent factories (definition built at query time) support this.
- The owner's nesting cap of one level equals `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`; the SDK default has moved to three levels, so the cap should be set explicitly rather than assumed, and re-checked on SDK upgrade.
- Because background is now the default for spawned subagents and rate-limit failures are not delivered as results, a pipeline that depends on a role's verdict must either request waiting or treat a missing report as "role did not run", not as "no findings".
- Orchestrator-decided fan-out over many roles maps to the Workflow tool or to separate `query()` calls, not to turn-by-turn model delegation.

### Gaps
- Agent teams: the current documentation page was not read; the feature-overview page in November 2026 lists dynamic workflows and cross-session messaging rather than "agent teams" in its comparison tabs, while the subagents page still mentions agent teams as "a coordinated team of sessions Claude spawns and supervises". Status and limits of agent teams are unverified.
- Hooks reference (exact payload of `SubagentStart`/`SubagentStop`, whether `SubagentStart` can block) was not read.
- Plugin-scoped agents ignore `hooks` and `permissionMode` frontmatter per the subagents page; other plugin restrictions were not checked.

## 4. Design rules that keep many roles from overlapping

### Takeaway
The sourced rules are few and consistent: decompose by context rather than by job title, give each delegated unit an objective, output format, tool guidance and boundaries, put "not for" conditions in the description, and let the orchestrator or a deterministic gate decide invocation for anything that must happen. The rest (size/risk gates, one role per finding class) is practice inferred from these, not separately evidenced.

### Cited Findings
- Decompose by context, not by problem type; confirm three things before adding an agent: "Genuine constraints exist" (context limits, parallelism, specialisation), "Decomposition follows context, not problem type", and clear verification points exist where a subagent can validate without full context. Closing rule: start with the simplest approach and add complexity only when evidence supports it. — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)
- Each subagent needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; without it agents duplicated work or left gaps. Effort-scaling rules were written into the prompt because agents cannot judge appropriate effort themselves. — [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Descriptions decide matching: "Write clear, specific descriptions so Claude can match tasks to the right subagent"; "If descriptions are vague or overlap, Claude may load the wrong skill or miss one that would help"; if a skill triggers too often, "make the description more specific" or disable model invocation; put the key use case first because listings are truncated. — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents); [Claude Code, Extend Claude Code](https://code.claude.com/docs/en/features-overview); [Claude Code, Skills](https://code.claude.com/docs/en/skills)
- Keep descriptions short, move detail into the system prompt that loads only when the agent runs. — [Claude Code, Subagents](https://code.claude.com/docs/en/sub-agents)
- Tool restriction as part of the role contract: "A tool you leave out isn't in the subagent's session at all"; common sets: read-only analysis `Read, Grep, Glob`; test execution `Bash, Read, Grep`; code modification `Read, Edit, Write, Grep, Glob`. — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- Model-decided versus orchestrator-decided: "Claude decides on its own when to spawn a subagent and how many to spawn"; either delegation instruction "only steers Claude, so set the limits as well"; "give explicit guidance on which scenarios warrant delegation, or set deterministic caps". For guaranteed use, name the agent. — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents); [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Role clarity has a measured but limited effect: in MAST, "disobey role specification" is only 1.5% of failures, and sharpening roles/hierarchy in ChatDev gave +9.4% task success, a verification step +15.6%. — [Why Do Multi-Agent LLM Systems Fail? v3](https://arxiv.org/html/2503.13657v3)
- Review-type roles: Opus 5 follows "only report high-severity issues" or "be conservative" literally and reports less; recommended is to "report everything and filter in a separate pass". — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Writer and checker should be separate contexts: verification subagents work because they need only artifact and criteria. — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)

### Inferences
- A workable definition template per role, derived from the above: one-sentence trigger ("Use when ..."), explicit non-goals ("Not for ..."), cardinality ("once", "once per candidate"), size/risk gate, input contract (what the caller must pass, since only the prompt string crosses), output contract (structured fields, evidence format such as file:line), tool set, model/effort, turn cap. The agent types already present in the owner's environment follow this trigger/non-goal/cardinality pattern.
- Overlap test before admitting a role: for a fixed set of sample tasks, could two descriptions both plausibly match? If yes, merge them or split along the artifact they consume (diff only, diff plus surrounding code, acceptance criteria only), since "context, not job title" is the evidenced boundary.
- Size or risk gates (e.g. only for L/XL changes) follow from the cost evidence: delegation "multiplies cost and time when applied to small tasks". The gate should be computed by the orchestrator (diff size, touched paths, labels) and expressed as "this role is available/required in this run", rather than left for the model to judge from the description.
- Since role-spec violations are rare but verification and termination failures are common, effort is better spent on output contracts, turn caps and a refuter/verifier step than on ever finer role wording.
- A catalogue of 40-50 is easier to keep disjoint as a two-level structure: few agent types (explorer, lens, verifier, designer, implementer) times parameterised skills/lenses, with the per-stage allowlist exposing only a handful.

### Gaps
- No primary source prescribes "explicit non-goals in descriptions" verbatim or measures its effect on mis-selection; it is inferred from the "vague or overlap" warnings and from the documented fix "make the description more specific".
- No published guidance on a maximum sensible number of agent definitions per orchestrator beyond the 15,000-token description warning.

## 5. Measuring whether a role earns its place; retirement criteria

### Takeaway
The only vendor-documented method is a with/without baseline: same realistic inputs, role on versus role off, compare pass rate against token and time overhead, and measure trigger rate separately from output quality. Public, vendor-independent precision numbers for AI review roles are scarce and inconsistent, so the owner has to measure on the system's own issues; the SDK exposes the needed signals (Agent tool calls, `parent_tool_use_id`, `total_cost_usd`, SubagentStart/Stop).

### Cited Findings
- DOC: "Seeing a skill trigger tells you Claude found it, not that it did what you intended. To know a skill is working, measure separately whether Claude invokes it on the prompts it should, and whether the output matches what you expect when it does. The check for both is a baseline comparison": realistic prompts, fresh session with the skill and again with it turned off. — [Claude Code, Skills](https://code.claude.com/docs/en/skills)
- DOC: skill-creator benchmark "aggregates pass rate, time, and tokens for with-skill versus without-skill ... so you can compare the pass-rate improvement against the token and time overhead"; blind A/B between two versions; description tuning via should-trigger / should-not-trigger prompts and hit rate. `claude plugin eval` runs each prompt with and without the plugin, scores with graders and exits non-zero below a threshold (CI gate). — [Claude Code, Skills](https://code.claude.com/docs/en/skills)
- DOC: `/skill-doctor` shows per-skill context cost and how often each is used and "flags skills in the listing that have never been invoked" (v2.1.252+). — [Claude Code, Skills](https://code.claude.com/docs/en/skills)
- DOC, instrumentation: detect invocation via `tool_use` blocks named `Agent`/`Task` with `subagent_type`; attribute messages via `parent_tool_use_id` / `agent_id`; each subagent's API requests count toward the query's `total_cost_usd`; `SubagentStart`/`SubagentStop` hooks with name matcher. — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents); [Claude Code, Subagents](https://code.claude.com/docs/en/sub-agents)
- MEASURED reference point for expected effect sizes: adding a verification step raised ChatDev task success by 15.6%, role clarification by 9.4%; authors still call the result insufficient. — [Why Do Multi-Agent LLM Systems Fail? v3](https://arxiv.org/html/2503.13657v3)
- MEASURED (vendor self-benchmark, treat with caution): Augment Code reports 65% precision / 55% recall for its reviewer on a 50-PR benchmark and 68% precision / 29% recall for a competitor. — [Augment Code, AI code review accuracy](https://www.augmentcode.com/guides/ai-code-review-accuracy)
- Vendor claim: Opus 5 "reviews code with high precision and recall ... its additional findings are mostly real issues rather than false positives. Accuracy holds at lower effort settings" (no numbers given). — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- OPINION/practice: a filtering layer should absorb false positives before a human sees them, and writer and checker should be separate agents because a model grading its own output grades generously. — [Augment Code, recall-first AI code review](https://www.augmentcode.com/guides/why-use-recall-first-ai-code-review)

### Inferences
- Metric set per role, derivable from pipeline data the orchestrator already has: (1) invocation rate = runs where the role was called / runs where its gate was true (separates "gate never fires" from "model never calls"); (2) yield = findings or artifacts per invocation; (3) precision = findings confirmed by the verifier or accepted by the next stage/human / findings raised; (4) unique contribution = confirmed findings no other role raised (overlap measure); (5) downstream effect = review bounce rate, rework commits, post-merge defects, time to merge for issues with versus without the role; (6) cost = tokens and USD per invocation and per confirmed finding; (7) failure rate = runs ending at maxTurns, in error, or without a valid structured result.
- Design of the comparison: prefer randomised on/off per issue within the same period over before/after windows, because model versions and issue mix change (the delegation behaviour differs between Opus 4.x and Opus 5). If only before/after is possible, hold model, effort and prompts constant and compare the same complexity classes. With a baseline around 48 bounces per 7 days, a role that prevents a few bounces needs several weeks to show an effect outside noise; small-sample results should be read as directional.
- Retirement criteria that follow: gate true but invocation rate near zero over a defined window (dead role: either force it or remove it); precision below a floor after the verifier (noise source); unique contribution near zero (subsumed by another role); cost per confirmed finding above what a human or the generalist stage costs; no measurable change in bounce/rework in an on/off comparison; high structural failure rate. A role failing one criterion should first be demoted (subagent to skill, model-invoked to orchestrator-invoked, always to gated) before deletion.
- Admission should mirror retirement: a new role enters with a stated hypothesis (which metric it moves), a gate, and a review date; without that, a 50-role catalogue cannot be pruned.
- The 48-of-1,686 finding is itself an invocation-rate measurement and, by the first criterion, means most existing subagent roles are currently unproven rather than proven useless: their quality has barely been sampled.

### Gaps
- No vendor-independent production measurement of precision or acceptance rate for multi-agent review pipelines was found; secondary sources cite a Tencent study (arXiv 2601.18844, 76% false positives among 433 alarms) and a "Martian Code Review Bench" (comment counts as useful when the developer later fixes the issue), neither verified at the primary source in this pass.
- No published thresholds (e.g. minimum precision or invocation rate) for retiring an agent role; the criteria above are inferred.
- No source quantifies how many issues are needed for a reliable on/off comparison in such a pipeline.

## 6. Cost and rate-limit implications; model tiering; prompt caching with many system prompts

### Takeaway
Each subagent is its own API conversation with its own system prompt, so 40-50 distinct role prompts mean 40-50 separate cache prefixes after the shared tool block; a role invoked rarely pays the cache-write price every time and reads little. Model tiering is supported per agent and the list-price spread is large (Haiku 5.5 input at $0.10 per million against $4 for Opus 5.5 and $8 for Fable 5.2), so narrow lenses on a small model with judgement on a large one is the documented pattern, with hard caps on depth, concurrency and spend as backstop.

### Cited Findings
- DOC, prices per million input tokens (base / 5-minute cache write / 1-hour cache write / cache read): Fable 5.2 $8 / $10 / $16 / $0.20; Opus 5.5 $4 / $5 / $8 / $0.20; Opus 5 $5 / $6.25 / $10 / $0.50; Sonnet 5.5 $2 / $2.50 / $4 / $0.10; Sonnet 5 $2 / $2.50 / $4 / $0.20; Haiku 5.5 (prompts up to 100K tokens) $0.10 / $0.125 / $0.20 / $0.01, above 100K $0.50 / $0.625 / $1 / $0.05; Haiku 4.5 $1 / $1.25 / $2 / $0.10. Cache write multipliers 1.25x (5 min) and 2x (1 h); cache read 0.1x by default, 0.05x on Opus 5.5 and Sonnet 5.5, 0.025x on Fable/Mythos 5.1 and 5.2. Minimum cacheable prompt 512 tokens on current models (1,024 on Sonnet 5, 4,096 on Haiku 4.5). — [Claude API, Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- DOC, cache structure: prefix order tools, then system, then messages; "Changing tool definitions invalidates everything"; changing the system prompt invalidates system and messages caches but leaves the tools prefix; matches require identical content up to the breakpoint; caches are isolated per organisation and (on the Claude API) per workspace. Cache hits are not deducted against the input-token rate limit. — [Claude API, Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- DOC: a subagent runs with "the agent's own system prompt, not the Claude Code system prompt", plus CLAUDE.md, preloaded skills and its tool definitions; "each subagent makes its own API requests, which count toward the query's total_cost_usd, and a subagent can spawn subagents of its own, so one prompt can grow into a tree of agents". — [Claude Code, Extend Claude Code](https://code.claude.com/docs/en/features-overview); [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- DOC, tiering: per-agent `model` and `effort`; the SDK docs' own example uses "a more capable model for high-stakes reviews" (`opus` if strict, else `sonnet`) built at query time; `CLAUDE_CODE_SUBAGENT_MODEL` sets a default for all subagents, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` forces it. An experimental per-agent `cacheTtl` field exists in the frontmatter list. — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents); [Claude Code, Subagents](https://code.claude.com/docs/en/sub-agents)
- DOC, effort as cost lever: on Opus 5, `low` and `medium` effort "produce strong quality at a fraction of the tokens and latency of higher settings"; review accuracy "holds at lower effort settings, which supports a fast pass at review time and a more thorough pass later"; "use low and medium liberally as your primary control for token cost". — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- DOC, caps: depth (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, default 3), concurrency (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, default 20), spend (`maxBudgetUsd`, no default limit; at the cap further spawns are refused, background subagents stopped, query ends with `error_max_budget_usd`). Requires TS SDK v0.3.219 / Python SDK v0.2.127 or later. — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- DOC, rate limits and subagents: "An API error that ends the subagent early, such as a rate limit, is never delivered as its result." — [Agent SDK, Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- Cost multipliers for orientation: 3-10x tokens for multi-agent versus single agent on equivalent tasks; Anthropic's original research system paired a large lead model with smaller subagents (Opus 4 lead, Sonnet 4 workers). — [Claude blog, Building multi-agent systems](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them); [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- Caching arithmetic for many roles: every distinct role prompt is a separate system-level prefix. With the 5-minute TTL, a role that runs once per issue and issues arrive more than five minutes apart never reads its own cache across issues; it only benefits within its own multi-turn run. Many rarely used roles therefore pay 1.25x on their prefix each time, while a few frequently used ones amortise. This argues for few agent definitions with stable shared prefixes (identical tool list and common preamble first, role-specific text last) and for putting role specifics into the task prompt or a skill rather than into 50 different system prompts.
- Keeping the tool block identical across roles preserves the tools-level cache even when system prompts differ; conversely, per-role tool lists (which the allowlist design encourages) create distinct tool prefixes and remove even that sharing. There is a real trade-off between tight per-role tool sets and cache reuse; tool restriction can alternatively be enforced by hook/permission while the declared tool list stays constant, at the price of the model seeing tools it may not use.
- Fixed start-up cost per subagent (own system prompt, CLAUDE.md, tool definitions, preloaded skills, the passed context) is paid on every spawn before any work happens. For a narrow lens the start-up can exceed the work; `omitClaudeMd`, minimal tool lists and short preloads reduce it. This is the mechanism behind "multiplies cost and time when applied to small tasks".
- Tiering sketch consistent with the sources: mechanical/narrow lenses (inventory, convention check with quotable rule, exploration) on Haiku 5.5 or Sonnet 5.5 at low effort; judgement roles (design critique, refutation, final review) on Opus 5.5 or Fable 5.2. At list input prices Haiku 5.5 is 40x cheaper than Opus 5.5 and 80x cheaper than Fable 5.2, so a wrong tier choice for a frequently spawned role dominates the cost of the catalogue.
- N roles per issue scale spend roughly linearly in spawned agents, not in defined agents: 50 definitions cost nothing until invoked (beyond description tokens). The budget question is "how many roles fire per issue of class S/M/L/XL", which the size gates of section 4 control; `maxBudgetUsd` per `query()` is the hard stop.
- Parallel fan-out of many roles concentrates input tokens into one minute and can hit rate limits; because a rate-limited subagent returns no result, the orchestrator needs an explicit "role did not report" state, and concurrency should be capped below the SDK default of 20 for subscription-limited setups.

### Gaps
- Output-token prices and current rate-limit tiers (ITPM/OTPM per model, subscription limits for Agent SDK use) were not retrieved; the caching page section on how cache writes count toward rate limits was truncated.
- Whether the Agent SDK places cache breakpoints so that the tools prefix is actually shared between parent and subagents with different tool subsets is not documented on the pages read; the `experimental.cacheTtl` field is undocumented beyond its name.
- No published per-issue cost figures for multi-role coding pipelines on current models were found.
